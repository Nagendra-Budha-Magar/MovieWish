# Security Report

This report covers the OWASP Top 10 (2021) categories.

## OWASP Top 10

| # | Category | How `MovieWish` defends against it (or why it doesn't apply yet) |
|---|----------|------------------------------------------------------------------|
| A01 | Broken Access Control | Every `/users` route requires `authenticate`, and role (RBAC) and ownership (ABAC) checks decide who may read, edit, delete or change roles. |
| A02 | Cryptographic Failures | Passwords are stored as salted scrypt hashes, tokens are signed JWTs, and Helmet sends HSTS so browsers only use HTTPS. |
| A03 | Injection | Zod `strictObject` schemas allow-list every field and reject non-string values (so `{"$ne": null}` fails), and names can only contain letters, spaces, `'`, `.` and `-`. There is no SQL yet, and Unit 3 will use parameterised queries or Prisma. |
| A04 | Insecure Design | Rate limits (300 requests / 15 min per IP, 5 failed logins / 15 min per IP + email), short-lived access tokens, refresh-token reuse detection, and body size limits are part of the design. |
| A05 | Security Misconfiguration | Helmet sets security headers and removes `X-Powered-By`, CORS only allows listed origins, errors use Problem Details with no stack traces, and the server refuses to start with a weak `JWT_SECRET`. |
| A06 | Vulnerable and Outdated Components | `npm audit` reports 0 vulnerabilities, the lock file pins versions, and Dependabot alerts are enabled on the GitHub repo. |
| A07 | Identification and Authentication Failures | Passwords need 8-72 characters with a letter and a digit, failed logins are rate limited, login errors are generic, and the refresh token lives in an httpOnly cookie. |
| A08 | Software and Data Integrity Failures | JWT signatures are verified with a pinned algorithm, issuer and audience, and installs use `npm ci` from the lock file. |
| A09 | Security Logging and Monitoring Failures | Each request gets a request ID and is logged. Alerting and monitoring are not set up yet and are planned for Unit 4. |
| A10 | Server-Side Request Forgery (SSRF) | Does not apply yet: the API never fetches user-supplied URLs (GitHub OAuth URLs are hard-coded and S3 keys are generated by the server). |

## Remaining weakness: in-memory rate limiting

**Problem.** The rate limiters (`express-rate-limit`) keep their counters in each Node process's memory. This causes two problems:

- Restarting the server resets all counters, so an attacker who can trigger a restart gets fresh login attempts.
- With several instances behind a load balancer such as Nginx, each instance counts separately, so the real limit becomes roughly 5 x N failed logins instead of 5.

This weakens the brute-force protection described under A04 and A07.

**Fix.** Move the counters to a shared store. Use `rate-limit-redis` with a Redis instance and pass it as the `store` option to both `apiRateLimit` and `authRateLimit`. All instances then share one count that survives restarts.
